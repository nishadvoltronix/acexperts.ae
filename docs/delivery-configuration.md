## Zoho contact form setup

`components/ContactForm.tsx` sends multipart `FormData` with browser `fetch` to `https://crm.zoho.com/crm/WebToLeadForm`. The public webform identifiers and tokens are centralized in [`lib/zoho-contact.ts`](../lib/zoho-contact.ts); they come from the supplied CRM export and are not API keys. This flow needs no Brevo credentials, PostgreSQL or local contact API. The exported analytics script is loaded lazily and its callbacks are retained. CSP permits the CRM connection and required analytics script.

JavaScript is required; a no-JavaScript notice offers telephone/email alternatives. The form shows an accessible status, prevents concurrent submissions and uses a 15-second timeout. Failures retain the input. Returned HTML is never executed. A successful client response does not prove that a lead is visible to its owner or that an email arrived; verify both in the intended account.

Public notice URL/version are intentionally rendered; credentials and state keys remain server-only.

Keep secrets in the runtime secret manager, never `NEXT_PUBLIC_`, client props, API responses, screenshots, logs, shell history or committed environment files. The sample contains empty placeholders. Do not place the database URL in a browser or query parameter. Configure application, proxy, database and provider-log access/redaction separately.

For the application APIs, missing/invalid required delivery or shared-state settings return a generic 503 without contacting Brevo. A failed shared database, wrong schema version, namespace/key mismatch or failed claim also prevents dispatch. A syntactically valid incorrect Brevo key reaches the provider and takes its generic rejection/error path. The forms can be built and browsed without credentials. API origin validation rejects foreign/cross-site requests; only explicit loopback aliases at matching scheme/port are equivalent during local testing.

## Exact Brevo setup steps

These steps apply to the newsletter and optional legacy contact API. They require the approved account owner/operator and controlled test inboxes. Sender and recipient settings for `CONTACT_FROM_EMAIL`/`CONTACT_TO_EMAIL` are unnecessary for the website's Zoho form. Account, DNS, hosting and live-send changes remain pending; production changes require explicit user authorization.

1. **Choose the account and isolate staging.** Use a dedicated staging newsletter list, an approved sender, and a controlled recipient inbox for `CONTACT_TO_EMAIL`. Keep staging list/template IDs separate from production. Confirm transactional sending is enabled and account credits/limits permit the planned tests. Record the account owner, test inbox aliases and approved HTTPS staging origin without publishing secrets or personal addresses.

2. **Authenticate the sender domain.** Open the account dropdown, then **Settings > Senders, Domains, IPs > Domains**. Add the domain after `@` in the approved sender address, or select **Authenticate** for an existing entry. Have the authorized DNS operator apply the exact Brevo-generated ownership, DKIM and DMARC records; values vary by account. Review any existing DMARC record before changing it. Return to Brevo and verify **Authenticated**. Brevo is rolling out a revised domain setup screen, so follow that account's guided authentication if shown. [Brevo domain authentication](https://help.brevo.com/hc/en-us/articles/12163873383186-Authenticate-your-domain-with-Brevo-Brevo-code-DKIM-DMARC).

3. **Create and verify the sender.** Go to **Settings > Senders, Domains, IPs > Senders > Add a sender**. Enter the approved From name and address and save. Authenticated-domain senders are automatically verified; otherwise complete the emailed six-digit verification flow. Put this address in `CONTACT_FROM_EMAIL`. The contact implementation sets the display name to `AC Experts website` and routes replies to the visitor's validated address. The newsletter sender is selected in its template separately. [Brevo sender setup](https://help.brevo.com/hc/en-us/articles/208836149-Create-a-new-sender-From-name-and-From-email).

4. **Generate a standard API key.** Go to **Settings > SMTP & API > API Keys & MCP > Generate a new API key**. Complete identity verification, name it for the AC Experts staging integration, select an expiry policy and generate. Store the one-time displayed value directly in the staging secret manager as `BREVO_API_KEY`. Keep it as a standard API key; this app uses neither an SMTP password nor an MCP key. Assign an owner for expiry/rotation. If unknown-IP blocking is enabled, authorize the staging server's actual egress IP through the account's approved process. [Brevo API keys](https://help.brevo.com/hc/en-us/articles/209467485-Create-and-manage-your-API-keys), [API IP authorization](https://help.brevo.com/hc/en-us/articles/5740111683858-Authorize-and-block-IP-addresses-for-API-and-SMTP-security).

5. **Create the confirmed newsletter list and obtain its ID.** Go to **CRM > Contacts > Lists > Create a list**, enter an unmistakable staging name, choose its folder and create it. Set `BREVO_NEWSLETTER_LIST_ID` to this list's numeric ID, not its folder ID. An authorized read of `GET /v3/contacts/lists` returns each list's `id` and `name`; paginate as needed and match both. Do not seed this list with unconfirmed addresses. [List creation](https://help.brevo.com/hc/en-us/articles/5526943347858-Create-folders-and-lists-to-organize-your-contacts), [list API](https://developers.brevo.com/reference/get-lists).

6. **Create the API double opt-in template.** Go to **Marketing > Templates > Create Template > Email template**. Name it for staging, select the verified sender, set a clear confirmation subject and include the business-approved newsletter purpose and consent wording. Set the confirmation button's URL to exactly `{{ params.DOIurl }}`. Save and activate the template. Set `BREVO_NEWSLETTER_DOI_TEMPLATE_ID` to its numeric ID; an authorized read of `GET /v3/smtp/templates?templateStatus=true` can verify the matching name, ID, active status and sender. A preview checks appearance; only the real DOI flow can verify its generated confirmation link. [Template creation](https://help.brevo.com/hc/en-us/articles/360019787120-Create-an-email-template), [template API](https://developers.brevo.com/reference/get-smtp-templates), [DOI API contract](https://developers.brevo.com/reference/create-doi-contact).

7. **Set redirect, origin and privacy settings.** Set `BREVO_NEWSLETTER_REDIRECT_URL` to an approved, working HTTPS destination after confirmation, and `FORM_ALLOWED_ORIGINS` to the exact staging origin (proposed `https://staging.acexperts.ae`, only after the hostname is approved and provisioned). The redirect belongs in environment configuration; the confirmation button retains the generated DOI link. Review the Brevo account/template tracking settings as described below. Publish the business-approved HTTPS privacy notice, set `PRIVACY_NOTICE_URL` and its immutable `PRIVACY_NOTICE_VERSION`, and set the owner-approved `NEWSLETTER_CONSENT_RETENTION_DAYS` before collecting signups. Both forms link the configured notice; newsletter delivery stays disabled when this configuration is incomplete.

8. **Configure newsletter unsubscribe and run acceptance checks.** In the newsletter campaign design, add Brevo's unsubscribe link (custom HTML uses `<a href="{{ unsubscribe }}">Unsubscribe</a>`) and choose the intended Brevo unsubscribe page. The app has no newsletter campaign sender, unsubscribe route or local confirmed-subscriber registry; Brevo handles these events. Marketing and transactional blocklists are distinct, so verify the actual marketing suppression outcome. Run the matrix below using controlled contacts before switching to production settings. [Brevo template link variables](https://help.brevo.com/hc/en-us/articles/4402386448530--Manual-Personalize-your-messages-with-dynamic-content-Brevo-Template-Language), [unsubscribe pages](https://help.brevo.com/hc/en-us/articles/208772629-Customize-an-unsubscribe-page-to-integrate-into-your-email-campaigns), [blocklist types](https://help.brevo.com/hc/en-us/articles/209458705-What-is-a-blacklisted-contact-).

The retained contact API uses Brevo's [transactional API](https://developers.brevo.com/reference/send-transac-email) with a fixed sender and recipient, visitor email as reply-to, and escaped HTML plus plain-text enquiry content. HTTP 201 with a nonempty `messageId` is required before returning acceptance. Acceptance means Brevo took responsibility for the request; it does not establish inbox arrival. The website contact form does not use this API.

The [double opt-in API](https://developers.brevo.com/reference/create-doi-contact) starts confirmation using `email`, `includeListIds`, `templateId` and `redirectionUrl`; the adapter accepts only HTTP 201. This is the API confirmation workflow. Brevo-hosted-form placeholder/automation instructions describe different workflows and must not replace the API's `{{ params.DOIurl }}` link. This implementation does not send a separate final welcome email. Existing-contact and re-subscription behavior are not established by the endpoint reference; verify them in the selected account.

## Shared PostgreSQL setup and operations

PostgreSQL is required for the newsletter and legacy contact API, not the Zoho form. The repository has a Node runtime and no selected hosting platform. The operator must supply a persistent shared database for the enabled APIs. All replicas, serverless invocations and overlapping releases for one environment must use the **same database, namespace and HMAC key**. A separate database and namespace isolate staging from production. Each form handler factory owns a pool of up to three connections. With contact and newsletter handlers, allow up to six connections per application worker, multiplied by worker processes and replicas; budget any managed connection pool accordingly. Pools are reused by handlers rather than created for each request.

1. Provision a private PostgreSQL database reachable only by the approved application/operator network. Require TLS and a certificate trusted by the Node runtime for remote hosts. The adapter deliberately rejects URL query/fragment options and supplies verified TLS itself; do not add `sslmode=disable` or disable certificate verification. Choose a provider connection endpoint compatible with normal transactions.
2. Use an owner/migration account to apply [`db/migrations/001-form-state.sql`](../db/migrations/001-form-state.sql) **once** with stop-on-error enabled. The application does not create or migrate its schema. The migration is deliberately non-idempotent: a second application should fail, not silently overwrite existing records. A securely configured local psql service avoids putting credentials in command text: `psql "service=acexperts-staging-owner" -v ON_ERROR_STOP=1 -f db/migrations/001-form-state.sql`. Provisioning this service/account is an operator task.
3. Create a separate login role through the provider's secure credential workflow; it must not own the schema or have superuser/DDL privileges. For a role named `acexperts_forms_runtime`, the migration owner grants only:

```sql
GRANT USAGE ON SCHEMA acexperts_forms TO acexperts_forms_runtime;
GRANT SELECT ON acexperts_forms.schema_version TO acexperts_forms_runtime;
GRANT SELECT, INSERT ON acexperts_forms.namespace_settings TO acexperts_forms_runtime;
GRANT SELECT, INSERT, UPDATE ON acexperts_forms.rate_limits,
  acexperts_forms.submissions, acexperts_forms.consent_events TO acexperts_forms_runtime;
```

4. Store that runtime role's connection URL, a newly generated state secret and the staging namespace in the hosting secret manager. The first operation binds the namespace to the key fingerprint. Different keys for the same namespace fail closed; changing namespace to bypass that check would bypass existing protections and is prohibited operationally. Coordinate key rotation with a drained deployment, provider reconciliation and an approved state migration.
5. Keep WAL-logged tables, persistent storage, `fsync`, `full_page_writes` and `synchronous_commit` enabled. The application explicitly requests synchronous commits. Define backup/restore, failover durability, connection limits and database monitoring; a local pass does not verify the provider's durability contract. Test restart/recovery and restrictive runtime privileges before live use.
6. Assign a restricted maintenance/operator role for reconciliation and retention. Runtime roles deliberately lack DELETE/DDL. Remove expired consent records according to the approved policy, including retained backups; monitor overdue `retain_until` rows. Retention timestamps do not execute deletions. Schedule the operator-only [retention script](../db/maintenance/form-state-retention.sql) using an explicitly approved scope, for example `psql "service=acexperts-staging-owner" -v ON_ERROR_STOP=1 -v form_scope=acexperts_staging -f db/maintenance/form-state-retention.sql` after that service and scope have been approved. It deletes only consent records past `retain_until` and accepted/rejected submission rows past their cooldown. It never removes pending/uncertain/timeout claims; those pseudonymous records also need an owner-approved retention and timely reconciliation policy. Never clear the namespace or bulk-delete unresolved claims to fix an error.

The locally provisioned portable PostgreSQL is a **synthetic test service**, not hosted staging or production infrastructure. Its binaries/data live under ignored `node_modules/.cache/acexperts-postgres/`; final integration results belong in the readiness report. Loopback-only synthetic identities and that temporary cluster's lifecycle must not be copied into a remote deployment. The isolated test cluster uses SCRAM password authentication.

## Consent and visitor behavior

The required newsletter checkbox starts unchecked. Its exact text and version are shared between rendering and audit code in [`lib/newsletter-consent.ts`](../lib/newsletter-consent.ts). The client sends `consent: true`, `consentVersion`, `noticeVersion`, a valid email and the empty spam trap; unknown fields and stale wording/notice versions are rejected. Set the approved notice URL/version before testing a live signup. If absent, the existing contact-data link remains and newsletter dispatch returns 503. When configured, both forms link the notice without changing their existing layout. The website does not add contact enquiries to the Brevo newsletter; review Zoho account integrations separately.

A new newsletter claim and its consent-request row commit atomically **before** a provider call. Records contain a keyed email hash, request UUID, server timestamp, exact wording/version, notice URL/version, origin, list/template IDs, retention deadline and delivery outcome. They contain no raw email, contact body or client IP. Hashes remain linkable personal-data evidence: restrict access and apply the approved retention policy. The stored row records a checked signup request, not verified ownership of the email.

Acceptance tells the visitor to check their inbox and confirm. The adapter only starts DOI; it never independently updates a contact, clears a blocklist or marks it subscribed. The audit schema deliberately constrains `confirmation_state` to `not_verified`. There is no confirmation/unsubscribe webhook or automatic Brevo reconciliation. The operator must retain verified provider confirmation and withdrawal evidence in an approved protected system and correlate it with the audit request/wording/template versions; do not infer confirmation from a redirect or change the database constraint to manufacture it. Verify the full existing/unsubscribed-contact lifecycle in the intended account.

Business approval remains required for the actual notice contents: controller/contact identity, enquiry and newsletter purposes, Zoho, Brevo and database processing, relevant transfers, retention and access/withdrawal requests. Approve applicability with the business's privacy adviser where needed. Supplying the environment URL/version is an operator declaration that the notice is approved; the parser cannot establish legal sufficiency. Preserve the published notice and DOI template version used in the evidence. The contact form technically operates without the notice configuration, so public enquiry collection still has an operational privacy gate.

The payload sets `contactPixelTrackingConsent: false`. Brevo documents that this anonymizes open/click events only when its per-contact tracking feature is enabled; otherwise the value is ignored. Verify the account/template and actual received mail. [DOI tracking semantics](https://developers.brevo.com/reference/create-doi-contact).

The newsletter prevents concurrent client submission and announces status in an accessible live region. It uses a 15-second browser deadline and resets only after HTTP 200 with a valid message. Failure preserves input; uncertainty never claims the request was definitely unsent. Contact has its own CRM AJAX status and timeout handling described above; actual lead creation and notification delivery require provider acceptance checks.

## Failure handling and duplicate scope

This section describes the Brevo application APIs. It does not apply to direct Zoho CRM submissions.

Provider requests have an eight-second deadline including receipt parsing, reject redirects and never expose provider debug text. Definite rejection returns 502; timeout returns 504; malformed/unexpected receipts, provider 408/409, provider 5xx and network ambiguity return a generic uncertain result. A provider 408/409 is not treated as definite non-delivery. No automatic provider retries occur.

Normalized submissions use a stable HMAC key and an atomic PostgreSQL claim. Only the claimant may dispatch. A simultaneous duplicate still pending returns 409; after acceptance, duplicates reuse the accepted outcome for **30 minutes**. Definite rejection has a **60-second** cooldown. The same behavior persists across instances/restarts when they share the required configuration and the database preserves committed records. After those finite windows, a new explicit submission can dispatch again; this is not indefinite uniqueness.

**Pending, uncertain and timeout claims never automatically expire or retry.** Process termination, an unknown COMMIT result or a failed final outcome write may leave a protected pending/uncertain claim. Even if the operator suspects no send occurred, reconcile against provider logs before releasing it. Record a restricted operator decision, supporting evidence and whether an explicit new submission is authorized. Do not automatically requeue it or delete it on restart. An uncertain provider result can represent an email already sent.

Legacy contact API delivery uses the durable claim UUID in `headers.idempotencyKey`. [Brevo's guide](https://developers.brevo.com/docs/heterogenous-versions-batch-emails) describes reuse of a UUID and a 30-minute TTL; its [transactional reference](https://developers.brevo.com/reference/send-transac-email) illustrates different header spelling/normalization. Actual provider behavior remains unverified. The database claim is the implemented cross-instance safeguard; no provider-level deduplication or DOI idempotency guarantee is assumed.

## Abuse controls and hosting prerequisites

These controls cover the local application APIs. Zoho receives website enquiries directly and requires its own verified provider controls.

The application retains validation, honeypots, exact origins, cross-site rejection, JSON-only uncompressed bodies, streamed size bounds (48 KiB contact; 4 KiB newsletter), a five-second body deadline, no-store/nosniff responses and secondary process-local caps. Enabled dispatch additionally requires atomic database budgets of **30 contact attempts and 10 newsletter attempts per database calendar minute**, shared by all instances of the namespace. Attempts that pass method/origin/content-type checks consume that shared budget before body parsing, including duplicates. The fixed-minute window is not a sliding window. Shared-store failures return 503 and prevent sending.

The global budgets intentionally do not trust browser-provided forwarding/IP headers. Add per-client controls at the trusted hosting ingress/WAF, which must overwrite untrusted forwarded identity and reject direct-origin bypass. Configure network/body/connection limits there as well. A global budget alone can deny legitimate visitors during an attack; per-client ingress controls remain a production prerequisite. Where sustained bot abuse warrants a challenge, verify it at the same trusted boundary without weakening current checks.
